# Publishing `advisor-review` to crates.io

This document describes how to publish the CLI and prepare each future version.

## One-time setup

1. Create or sign in to a [crates.io](https://crates.io) account.
2. Create an API token from the account settings.
3. Authenticate Cargo locally:

   ```bash
   cargo login
   ```

   Paste the token when prompted. Never commit the token or put it in `Cargo.toml`.

4. Confirm that the package name `advisor-review` is available on crates.io. A crate name cannot be reused if another owner already published it.

## Package metadata

The publishable metadata lives in `[package]` in `Cargo.toml`:

| Field | Current value | Change when |
|---|---|---|
| `name` | `advisor-review` | Only before the first release, or when intentionally publishing a differently named crate. |
| `version` | `0.1.0` | Every release; follow Semantic Versioning. |
| `description` | Local-first advisor review tooling for LaTeX manuscripts | The package's public purpose changes. |
| `repository` | GitHub repository URL | The canonical source repository changes. |
| `homepage` | GitHub repository URL | The project homepage changes. |
| `readme` | `README.md` | The package landing documentation moves. |
| `license` | `MIT` | Only if the project's licensing changes. Keep `LICENSE` consistent. |
| `rust-version` | `1.85` | The minimum supported Rust version changes. The repository pins Rust 1.85.0 in `rust-toolchain.toml`. |
| `keywords` | LaTeX/research/manuscript/review/CLI | Search terms change; crates.io allows at most five. |
| `categories` | `command-line-utilities` | The package's crates.io category changes. |
| `exclude` | Local agent/OpenSpec files | Files that should not be shipped change. |

Do not put API keys, provider credentials, manuscript data, or local development configuration into package metadata.

## Versioning policy

Update `version` in `Cargo.toml` before every publish:

- Patch, for example `0.1.0` → `0.1.1`: bug fixes, documentation, or internal changes without new public behavior.
- Minor, for example `0.1.1` → `0.2.0`: backward-compatible features or new CLI capabilities.
- Major, for example `0.2.0` → `1.0.0`: breaking CLI, configuration, output-schema, or library API changes.

Once a version has been published, that exact version cannot be published again. Create a new version instead.

## Release checklist

From the repository root:

```bash
# 1. Update version and any changed metadata in Cargo.toml.
# 2. Run formatting and tests.
cargo fmt --all -- --check
cargo test

# 3. Inspect exactly what will be packaged.
cargo package --list

# 4. Build and validate the crate without uploading it.
cargo publish --dry-run

# 5. Review the generated package if needed.
cargo package

# 6. Commit the release metadata and create a tag.
git add Cargo.toml Cargo.lock README.md PUBLISHING.md
git commit -m "Release advisor-review v<VERSION>"
git tag -a "v<VERSION>" -m "Release advisor-review v<VERSION>"
git push origin main --tags

# 7. Upload the package.
cargo publish
```

Replace `<VERSION>` with the exact value in `Cargo.toml`, such as `0.1.0`. The `cargo publish --dry-run` step must pass before uploading.

## After publishing

Verify the package page and generated documentation:

```text
https://crates.io/crates/advisor-review
https://docs.rs/advisor-review
```

Test installation from the registry rather than the local checkout:

```bash
cargo install advisor-review --version <VERSION>
advisor-review --help
```

If a published version contains a serious problem, investigate yanking that version through crates.io. Yanking prevents new dependency resolution from selecting it but does not delete the package or invalidate existing lockfiles.

## What belongs in the crate

The package should contain the Rust sources, manifest, lockfile as generated by Cargo, README, license, and user-facing documentation. Repository-only agent instructions, OpenSpec planning artifacts, and Claude command files are excluded by `Cargo.toml` and should not be part of the published package.
